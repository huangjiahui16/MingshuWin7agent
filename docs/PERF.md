# 性能实测：到底慢在哪（明枢Win7）

> 数据来自 `python docs\bench_perf.py`（10 个任务、每个 4 次模型往返、固定 500ms 模拟 API 延迟；
> 工具是真实执行的本地读写，不是假的）。

## 一、三段占比

| 分段 | 占比 | 次数 | 平均耗时 | 合计 |
|---|---|---|---|---|
| 本地执行（列目录/读文件/搜索） | **0.4%** | 30 | **2.4 ms** | 72 ms |
| 模型网络（等 API 返回） | **99.6%** | 40 | **508.7 ms** | 20350 ms |
| 界面渲染 | 0%（无界面） | 0 | — | — |

一次模型往返 ≈ **212 个**本地工具调用的时间。

**结论：所谓“Win7 上读写不如 WorkBuddy”，不成立。** 同硬件下 NTFS 顺序读写 Win7 与 Win11 基本一致，
时间几乎全部花在等模型返回。要提速只能砍轮次（快路径、少工具循环、缓存上下文），改读写代码收益是千分之一级。

## 二、这次针对读写做的优化（都已生效）

| 优化 | 改动 | 效果 |
|---|---|---|
| 目录枚举 | `os.listdir + 逐个 stat` → `os.scandir` 一次取全 | 目录列举快 2~5 倍 |
| 目录缓存 | 列表结果 3 秒 TTL（模型常连着两轮看同一目录） | 第二次列举 0.09ms（实测） |
| 编码探测 | 全文多遍解码 → **只探前 64KB**，命中后全文解一次；顺序 utf-8-sig → utf-8 → gbk → utf-16 | 大文件读取不再反复解码 |
| 文本缓存 | <256KB 的小文件内容缓存（LRU，60 个） | 重复读 50 次共 2.8ms |
| 大文件 | 只读到需要的那一段（按 max_chars 估字节），不整文件读入 | 几十 MB 的日志也能秒开 |
| 搜索 | 默认只下钻 **3 层**，超过 100 结果 / 5000 目录 / 20 秒就早停 | 不再默认全盘 walk 几分钟 |
| 中文乱码修复 | `read_file` 原来硬编码 UTF-8 读，GBK 文件全是乱码 | 中文文件终于读对了 |

顺便修了一个真 bug：`read_file` / `grep_files` 以前用 `encoding="utf-8", errors="replace"`，
在中文机器上打开 GBK 文本会整篇变问号——这才是“Win7 读写差”的真实体感来源之一。

## 三、如果实测本地占比确实高，按这个顺序继续

1. **确认硬盘模式**：设备管理器 → IDE ATA/ATAPI 控制器，跑在 IDE 模式而不是 AHCI，吞吐差 30%~50%；
2. **杀软**：360/火绒逐文件扫描会拦每一次 open，加白名单；
3. **索引服务**：Win7 默认关闭 Windows Search，这是“搜索比 Win11 慢”的真正原因；
   要么引导用户开服务，要么就按现在的限深搜索；
4. **网络盘**：SMBv1 在 Win7 默认启用，局域网路径读写会明显慢（换 SMBv2 有安全权衡）。

## 四、三道资源墙（已实现并实测通过）

| 墙 | 实现 | 实测结果 |
|---|---|---|
| 内存墙 | Job Object：`ProcessMemoryLimit=300MB`、`ActiveProcessLimit=4`、`KILL_ON_JOB_CLOSE` | 查询内核确认：314572800 字节 / 4 进程 |
| CPU 墙 | 工作线程 `THREAD_PRIORITY_IDLE`（-15）；可配置整进程 IDLE | `GetThreadPriority` 读回 **-15** |
| I/O 墙 | 工作线程 `THREAD_MODE_BACKGROUND_BEGIN` | 返回成功，状态 `background` |

**为什么 CPU 墙打在工作线程而不是整个进程**：Tk 的事件循环和绘制都在主线程，
整进程降到 IDLE 会让用户点按钮都要排队，界面发涩。工作线程降级同样是内核调度生效。
想要更狠可以把 `[agent] cpu_wall` 改成 `process`。

不绑 CPU 亲和性：老机器多是单核/HT 双核，绑核常把 Agent 和用户程序挤进同一个物理核，反而更卡。
